📋 1. Descripción y Objetivos del Proyecto

El propósito de esta práctica es implementar y comprobar lógica de negocio dentro del motor de base de datos PostgreSQL mediante la articulación desacoplada de:

  • Una función escalar pura: Para calcular ajustes porcentuales sin efectos colaterales ni mutación de tablas.
  • Un procedimiento almacenado: Para orquestar validaciones de existencia, llamar la función escalar y actualizar el precio unitario del catálogo.
  • Un disparador (Trigger) y su función asociada: Para auditar automáticamente cualquier cambio efectivo de precio con fecha, hora y usuario activo.
⚠️ Regla Crítica de Negocio: No se deben modificar precios históricos en la tabla de facturación ("InvoiceLine"). El cambio afecta únicamente al catálogo activo de pistas ("Track"). Además, se debe trabajar estrictamente en una copia de la base de datos Chinook para preservar la base original sin modificaciones.

Fase 2: Función Escalar de Cálculo de Precio (sql/02_funcion_escalar.sql)

Implementa la lógica pura de cálculo matemático sin afectar ninguna tabla, con validación defensiva de errores.

sql/02_funcion_escalar.sql 
CREATE OR REPLACE FUNCTION calcular_precio_ajustado(
    precio_actual NUMERIC, 
    porcentaje    NUMERIC
)
RETURNS NUMERIC AS $$
DECLARE
    v_precio_calculado NUMERIC(12, 4);
    v_precio_final     NUMERIC(10, 2);
BEGIN
    -- Rechazo de NULLs
    IF precio_actual IS NULL THEN
        RAISE EXCEPTION 'Parámetro inválido: El precio actual no puede ser nulo (NULL).'
            USING ERRCODE = 'check_violation';
    END IF;

    IF porcentaje IS NULL THEN
        RAISE EXCEPTION 'Parámetro inválido: El porcentaje de ajuste no puede ser nulo (NULL).'
            USING ERRCODE = 'check_violation';
    END IF;

    -- Validación de precio inicial > 0
    IF precio_actual <= 0 THEN
        RAISE EXCEPTION 'Valor fuera de rango: El precio actual (%), debe ser estrictamente mayor que cero.', precio_actual
            USING ERRCODE = 'numeric_value_out_of_range';
    END IF;

    -- Validación de porcentaje [-50, 100]
    IF porcentaje < -50 OR porcentaje > 100 THEN
        RAISE EXCEPTION 'Porcentaje no permitido: El porcentaje (%) está fuera del rango [-50, 100].', porcentaje
            USING ERRCODE = 'numeric_value_out_of_range';
    END IF;

    -- Fórmula matemática y redondeo a 2 decimales
    v_precio_calculado := precio_actual * (1.0 + (porcentaje / 100.0));
    v_precio_final := ROUND(v_precio_calculado, 2);

    -- Rechazo de resultado redondeado <= 0
    IF v_precio_final <= 0 THEN
        RAISE EXCEPTION 'Resultado inválido: El precio ajustado resultante (%), debe ser mayor que cero.', v_precio_final
            USING ERRCODE = 'check_violation';
    END IF;

    RETURN v_precio_final;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

Fase 3: Procedimiento Almacenado de Aplicación (sql/03_procedimiento.sql)

Valida la existencia del producto en el catálogo, llama a calcular_precio_ajustado y realiza la actualización.

sql/03_procedimiento.sql 
CREATE OR REPLACE PROCEDURE aplicar_ajuste_precio(
    id_producto INTEGER, 
    porcentaje  NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_precio_actual NUMERIC(10, 2);
    v_precio_nuevo  NUMERIC(10, 2);
BEGIN
    IF id_producto IS NULL THEN
        RAISE EXCEPTION 'Parámetro inválido: El identificador del producto no puede ser nulo (NULL).'
            USING ERRCODE = 'check_violation';
    END IF;

    IF porcentaje IS NULL THEN
        RAISE EXCEPTION 'Parámetro inválido: El porcentaje de ajuste no puede ser nulo (NULL).'
            USING ERRCODE = 'check_violation';
    END IF;

    -- Comprobar existencia en catálogo
    SELECT "UnitPrice" INTO v_precio_actual
    FROM "Track"
    WHERE "TrackId" = id_producto;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Producto no encontrado: No existe ninguna pista con identificador (TrackId = %).', id_producto
            USING ERRCODE = 'data_exception';
    END IF;

    -- Reutilización obligatoria de la función escalar
    v_precio_nuevo := calcular_precio_ajustado(v_precio_actual, porcentaje);

    -- Actualización exclusiva
    UPDATE "Track"
    SET "UnitPrice" = v_precio_nuevo
    WHERE "TrackId" = id_producto;

    RAISE NOTICE 'Ajuste completado en TrackId %: Anterior = %, Nuevo = %', id_producto, v_precio_actual, v_precio_nuevo;
END;
$$;

Fase 4: Trigger y Función Disparadora (sql/04_trigger_y_funcion.sql)

Garantiza la trazabilidad automática comparando el estado OLD y NEW con IS DISTINCT FROM.

sql/04_trigger_y_funcion.sql 
CREATE OR REPLACE FUNCTION fn_auditar_cambio_precio()
RETURNS TRIGGER 
LANGUAGE plpgsql
AS $$
BEGIN
    -- Comparación estricta de cambio real
    IF NEW."UnitPrice" IS DISTINCT FROM OLD."UnitPrice" THEN
        INSERT INTO auditoria_precios_track (
            id_pista,
            precio_anterior,
            precio_nuevo,
            fecha_cambio,
            usuario_db
        ) VALUES (
            OLD."TrackId",
            OLD."UnitPrice",
            NEW."UnitPrice",
            CURRENT_TIMESTAMP,
            CURRENT_USER
        );
    END IF;

    RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS trg_auditar_cambio_precio ON "Track";

CREATE TRIGGER trg_auditar_cambio_precio
AFTER UPDATE OF "UnitPrice" ON "Track"
FOR EACH ROW
EXECUTE FUNCTION fn_auditar_cambio_precio();

🎓 5. Conclusiones Técnicas y Fundamentación

Diferencias Conceptuales y Operativas: Función Escalar, Procedimiento y Disparador

Dentro del motor PostgreSQL, cada uno de estos tres objetos cumple un rol arquitectónico específico y no deben confundirse:

  • Función Escalar (FUNCTION ... RETURNS NUMERIC): Es un objeto puramente determinista y computable. Recibe parámetros escalares y retorna obligatoriamente un único valor atómico. No modifica el estado de la base de datos (no ejecuta DML), lo que permite invocarla libremente dentro de consultas SELECT, expresiones WHERE o fórmulas de cálculo sin provocar efectos colaterales.
  • Procedimiento Almacenado (CREATE PROCEDURE ... CALL): Diseñado para orquestar lógica de negocio y procesos que implican efectos colaterales (inserciones, actualizaciones o eliminaciones en tablas). No devuelve un valor mediante RETURN, sino que se ejecuta mediante la instrucción CALL. Tiene la capacidad de gestionar límites de transacciones autónomas y consolidar reglas de validación previas a la persistencia.
  • Disparador (TRIGGER y su función de soporte): Es un mecanismo reactivo e implícito. No es invocado directamente por un usuario o aplicación, sino que el propio motor de PostgreSQL lo ejecuta de manera automática ante la ocurrencia de un evento del ciclo de vida de los datos (en este caso, AFTER UPDATE OF "UnitPrice"). Su propósito es salvaguardar reglas de integridad y trazabilidad que jamás deben poder ser eludidas.

¿Por qué la auditoría NO depende de la voluntad o memoria del usuario?

Al delegar la inserción de auditoría a un Trigger a nivel de base de datos en lugar de programarlo manualmente en el procedimiento almacenado o en el código del software cliente:

  1. Garantía Ineludible (Mecanismo Centralizado): Cualquier vía de modificación (sea una aplicación web, un microservicio, el procedimiento almacenado aplicar_ajuste_precio, un script administrativo o una consulta UPDATE manual ejecutada por un DBA en consola) activará forzosamente el trigger. El desarrollador o usuario no puede "olvidar" auditar el cambio.
  2. Atomicidad e Integridad ACID: La acción del trigger forma parte intrínseca de la misma transacción que modifica el catálogo. Si la actualización se revierte (por un error o ROLLBACK), la auditoría se revierte conjuntamente. Nunca existirán auditorías ficticias ni modificaciones no auditadas.
  3. Separación de Responsabilidades: El procedimiento almacenado se enfoca en la orquestación del negocio (verificar catálogo y llamar la función matemática), mientras que la persistencia probatoria y de cumplimiento normativo queda blindada en el nivel más bajo: el motor relacional.
